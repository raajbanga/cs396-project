\begin{abstract}
\noindent
epaData is a web application for managing the annual operating and emissions data of U.S.\
power-plant units published through the EPA Clean Air Markets Program Data (CAMPD) service. It
retrieves data from the CAMPD API, validates and imports CSV and Excel files, stores the result
in a relational SQLite database, and supports searching, ranking, comparing, inspecting, and
exporting it. The committed database holds 1,619 facilities, 5,204 generating units, and 50,947
unit-year records for the reporting years 2015--2026. Imports made through the interface are
compared with the stored data and saved only on the user's approval; rows that fail validation
are retained in a data-quality report, and every record can be traced to the retrieval or file
that last wrote it. Searches may be expressed as filters, numeric ranges, or plain-English
descriptions, which a rule-based parser translates into the same filters. This report documents
the design, implementation, and evaluation of the system and the limitations carried into
Phase~2.
\end{abstract}

\section{Project description}
\label{sec:description}

\subsection{Problem}

Fossil-fuel power plants subject to federal programs such as the Acid Rain Program and the
Cross-State Air Pollution Rule must report their fuel use, electricity generation, and
emissions of sulfur dioxide (\SOtwo), nitrogen oxides (\NOx), and carbon dioxide (\COtwo). The
U.S.\ Environmental Protection Agency publishes these reports through CAMPD, both as
downloadable files and through a REST interface, the CAM API. For every generating unit the
data give annual operating time, gross load, heat input, and emitted mass, together with the
unit's fuel, type, and pollution-control equipment.

The data are authoritative but difficult to query. Answering a question such as \emph{``Which
coal units in Kentucky emitted more than 500{,}000 tons of \COtwo{} in 2025?''} requires calling
the correct endpoint with the correct parameters, joining the result with facility metadata,
and applying a numeric threshold; a comparison across years requires one request per year.
Analysts who receive CAMPD extracts as spreadsheets have no simple means of checking them for
missing values, out-of-range numbers, or repeated facility-unit-year records, or of seeing how
they differ from data already held. Once several sources are combined, the origin of each
figure is easily lost.

\subsection{Intended users}

The system serves three groups: students and researchers who need emissions data without
writing API code; environmental and energy analysts who combine CAMPD data with their own
spreadsheet extracts and need those files validated and reconciled; and reviewers and
regulators who must trace a figure to its source and see which records were rejected and why.
No user is assumed to know SQL or the structure of the CAM API, so searches are expressed
through forms, tables, and plain-English descriptions.

\subsection{Objectives}

The course project description defines twelve learning objectives for the two-phase project.
Phase~1 addresses the nine concerned with data management:
\begin{enumerate}[label=O\arabic*.]
  \item Design a web-based information system with a front end and a database back end.
  \item Develop server routes, page templates, forms, and interactive web components.
  \item Design and implement a relational database using SQLite and an object-relational mapper.
  \item Retrieve environmental data from public sources or import downloaded files.
  \item Validate, clean, transform, and store uploaded data.
  \item Implement database search, filtering, sorting, and pagination.
  \item Export selected data and calculated results.
  \item[O11.] Test and deploy a complete data-driven web application.
  \item[O12.] Document data sources, assumptions, equations, units, and system limitations.
\end{enumerate}
Objectives O8--O10 (environmental indicators, multi-indicator scoring, and interactive charts of
evaluation results) belong to Phase~2. Section~\ref{sec:testing} assesses each Phase~1
objective.

\subsection{Scope}

Phase~1 delivers a data-management system rather than an evaluation tool. It covers retrieval
of annual apportioned emissions from the CAM API; upload of CSV and Excel files in the CAMPD
column layout; validation and storage in SQLite; basic, multi-constraint, ranking, and
description-based search; facility and unit details and comparison; and CSV export of
datasets, search results, selections, valid and invalid records, and provenance. The EPA TRACI
characterisation factors~\cite{bare2011traci}, environmental-impact indicators, and the weighted
scoring model are deferred to Phase~2. Sub-annual (hourly to monthly) data are displayed on
demand from the API but not stored, and the application runs locally
(Section~\ref{sec:limitations}).

\section{Functions implemented}
\label{sec:functions}

epaData is a single-page application. The pages listed in the specification are realised as a
home view, four explorer tabs (Facilities, Units, Map, Audits), the Retrieve, Upload, and
Download dialogs opened from the header, and the facility, unit, and comparison dialogs opened
from the tables. This section describes each function from the user's perspective;
Section~\ref{sec:design} explains how the functions are built, and Section~\ref{sec:features}
examines the most significant of them in detail.

\subsection{Home view}

The home view (Figure~\ref{fig:home}) introduces the project and presents four numbered
buttons in workflow order: Retrieve, Upload, Search, and Download. A coverage strip gives the
number of unit-year records per reporting year, summarises the datasets by source (for example,
``EPA CAMPD API $\cdot$ 12 active (+18 superseded)''), and states which views read the local
database and which call the EPA API live. Five tiles summarise facilities, installed capacity,
reliability regions, total \COtwo{} over all years, and data-quality flags.

\subsection{Data retrieval from the EPA API}

The \textbf{Retrieve} dialog queries the CAM API's apportioned annual emissions with the
filters the specification requires: a range of reporting years, state, facility IDs, fuel type,
unit type, and control technology. The fuel, unit-type, and control options are loaded from
CAMPD's master-data endpoints, so every choice is a value the API accepts. While the form is
edited, a panel titled \emph{Already in the database} reports how many matching unit-years are
stored and which dataset last wrote them. \textbf{Preview} fetches the data without saving and
classifies every record as new, changed, unchanged, or dropped, showing the stored and incoming
value of each differing field; \textbf{Approve \& save} stores each year as a new dataset. A
history table lists every past retrieval with its parameters, date, status, and counts. The API
key is held in a server-side environment variable and never reaches the browser.
Section~\ref{sec:feat-retrieve} presents a worked example.

\subsection{File upload and validation}

The \textbf{Upload} dialog accepts a CSV or Excel file of up to 100\,MB by drag-and-drop or
file picker; the extension and size are checked in the browser and again on the server. A
Python script maps the file's headers to database columns, validates every row, and detects
repeated facility-unit-year records. Before anything is written, the dialog reports the counts
of valid, rejected, duplicate, and flagged rows; compares the valid records with the database;
and lists each rejected row with its column, value, and reason, the repeats within the file,
the records already in the database with the fields that would change, and the column mapping.
A daily or hourly CAMPD file, whose metrics have no place in an annual schema, is recognised as
such, and the dialog states that only its facility and unit attributes will be stored. On approval, the valid records, the rejected and duplicate
rows, the upload metadata, and a copy of the original file are stored, and the rejected rows
can be downloaded directly from the confirmation (Section~\ref{sec:feat-upload}).

\subsection{Search}

The Facilities and Units tabs share one filter bar. The Facilities tab shows one row per plant
with totals; the Units tab shows one row per unit and reporting year, the grain of the stored
records.

\paragraph{Basic search.} A text box matches facility names, owners and operators, counties,
and facility IDs. Selects in the toolbar filter by state, NERC region, and primary fuel, and a
\emph{More filters} panel adds facility ID, unit ID, reporting year, county, secondary fuel,
unit type, \SOtwo/\NOx/PM control, operating status, audit flag and severity, and record origin
(API or file upload).

\paragraph{Multi-constraint and range search.} All filters combine conjunctively. Inclusive
minimum and maximum bounds are available for reporting year, operating time, gross load, heat
input, and \COtwo, \SOtwo, and \NOx{} mass, and every active filter appears as a removable chip
above the table (Section~\ref{sec:feat-ranking}).

\paragraph{Description-based search.} A \emph{Name\,|\,Describe} switch turns the search box
into a sentence input. A description such as ``Find coal units in Kentucky with high CO2
emissions'' is translated into the same filters, which appear as chips and in the filter
controls for further refinement; words that could not be interpreted are listed rather than
ignored (Section~\ref{sec:feat-describe}).

\paragraph{Ranking and comparison.} Any metric column can be sorted, and a \emph{Ranking}
control retains the first $N$ rows of that order, overall or per state, which covers the
specification's top-$N$, bottom-$N$, and group-and-rank searches. Two to four facilities or
units can be selected for side-by-side comparison. Historical searches use the year range or
the unit dialog, which lists every reporting year of a unit.

\paragraph{Result handling.} Results are paginated (10 to 100 rows per page) and sortable on
every column with a meaningful order, and each unit row opens the unit dialog. A \textbf{CSV}
button downloads every matching row across all pages. The tab, filters, sort, and page are
encoded in the URL query string, so any search can be bookmarked, shared, and reloaded.

\subsection{Facility and unit details}

The facility dialog shows the plant's identification (ID, county, state, EPA and NERC region,
owner), its units with their fuels and controls, its year-by-year operation and emissions, and
its audit flags. A granular view in the same dialog shows hourly, daily, weekly, or monthly data
fetched live from the API, alongside yearly totals from the database. The unit dialog
(Figure~\ref{fig:unit}) shows identification, fuel and controls, programs, every reporting year
with the dataset that supplied it and the controls and programs reported for that year, and any
sanity flags.

\subsection{Comparison, map, and audits}

The comparison dialog (Figure~\ref{fig:compare}) places two to four facilities or units side by
side for the latest reporting year: capacity, generation, operating hours, capacity factor,
carbon intensity, heat rate, fuels, and control coverage. The Map tab draws every facility with
coordinates on a three-dimensional globe or a two-dimensional Leaflet map, sized by capacity or
\COtwo{} and coloured by fuel (Figure~\ref{fig:map}); the 37 facilities for which CAMPD has no
coordinates are listed beneath the map, rather than silently omitted. The Audits tab lists every
physical-sanity flag with its rule, severity, and explanation, paginated and filterable.

The \textbf{Download} dialog (Figure~\ref{fig:download}) provides the six CSV exports the

\section{System design}
\label{sec:design}

\subsection{Architecture}

epaData is a single Next.js application containing both the user interface and the server
(Figure~\ref{fig:arch}). The first page load is rendered on the server with its data already
fetched; subsequent interactions call the server through typed tRPC procedures or two HTTP
route handlers. Every database query is built with the Drizzle ORM and executed against a
single SQLite file through the libSQL client. Only two kinds of work leave the Node.js process:
reading uploaded files, which is delegated to a Python subprocess, and calls to the EPA CAM API
and, optionally, the OpenRouter language-model service.

The source tree mirrors these layers. \code{src/app} contains the page and its React
components. \code{src/server/api} defines the tRPC router, whose procedures validate their input
with Zod and delegate to \code{src/server}, which holds the query builders, the CAMPD client,
the upload and export modules, and the shared write path. \code{src/lib} contains logic with no
database or network access: filter and URL state, the description parser, record comparison,
emissions arithmetic, and CSV formatting. Keeping this logic pure makes it testable with plain
unit tests (Section~\ref{sec:testing}). The command-line scripts in \code{scripts/} import the
same modules, so a command-line sync and an in-app retrieval execute identical code.

\subsection{Life cycle of a search}

Tracing one search through the system illustrates how the components interact. Suppose a user
opens the Units tab, selects Kentucky and Coal, sets the year to 2025, and enters a minimum
\COtwo{} of 500{,}000~tons.

\begin{enumerate}
  \item Each change updates a filter object in React state, which the pure function
        \code{explorerSearchParams} mirrors into the URL, so the browser history and any shared
        link carry the full search:\\[2pt]
        {\small\code{?tab=units\&stateCode=KY\&primaryFuel=Coal\&year=2025\&co2MassTonsMin=500000}}
  \item A deferred copy of the filters is passed to \code{api.facilities.getUnitYears.useQuery}.
        Deferral keeps typing responsive; TanStack Query keeps the previous page on screen
        until the new one arrives and caches each distinct query.
  \item On the server, Zod validates the input against \code{facilityFilterSchema} extended
        with paging and sort fields, rejecting unknown sort keys and out-of-range page sizes.
  \item \code{rankedUnitYears} builds a single SQL statement: \code{annual\_records} joined to
        \code{units}, \code{facilities}, and \code{datasets}; a WHERE clause assembled from
        facility, unit, and record condition builders; and a \code{ROW\_NUMBER()} window over
        the requested sort (Listing~\ref{lst:rank}).
  \item \code{pageOf} runs two queries over the same ranked subquery, one for the page of rows
        and one for the total count. SQLite answers in about 6\,ms using the
        \code{(year, co2\_mass\_tons)} index.
  \item The table renders 25 rows across three pages. Its \textbf{CSV} button calls
        \code{/api/export?type=search\&\ldots} with the same query string, which the handler
        parses with the same \code{parseExplorerParams} function before running
        \code{rankedUnitYears} without a page limit, so the file contains exactly the rows the
        table showed.
\end{enumerate}

On reload, \code{page.tsx} parses the URL on the server, prefetches the same query, and sends
the rendered table with its data embedded, so a shared link opens directly on the results.

\subsection{Database schema}

Figure~\ref{fig:er} shows the six tables and their relationships. Following the relational
model~\cite{codd1970}, each table holds one kind of entity identified by a key, and
relationships are expressed through foreign keys. The design follows the real-world hierarchy
of the data: a \emph{facility} (a power plant, identified by its EPA ORISPL code) houses one or
more \emph{units} (boilers, turbines, or engines), each of which reports one \emph{annual
record} per year. Two tables record provenance: \emph{datasets} has one row per retrieval or
upload, and \emph{import\_issues} one row per rejected or skipped source row. The sixth table,
\emph{data\_audit\_logs}, holds the physical-sanity flags raised on annual records.

\paragraph{Keys and integrity rules.} Integrity rules are enforced by the database rather than
by application code alone. \code{facilities.id} is the EPA facility ID itself: being stable and
meaningful, it serves directly as the primary key and appears in URLs and exports. EPA's unit
ID (``1'', ``CT1'', \ldots) is unique only within a facility, so \code{units} has a surrogate
UUID key and a unique index on \code{(facility\_id, unit\_id)}, which upserts use as their
conflict target. An annual record is unique per \code{(unit\_internal\_id, year)}, the
specification's ``facility-unit-year'', and its primary key is derived from the same pair
(\code{\$\{unitInternalId\}\_\$\{year\}}), so re-importing a year updates the existing row
rather than inserting a duplicate. Metric columns are nullable \code{REAL}: \code{NULL} records
that the source did not report a value, which is distinct from a reported zero. Totals treat
\code{NULL} as zero, while range filters, percentile thresholds, and the sanity rules skip it,
and the derived rates are \code{NULL} whenever an input is missing or gross load is zero. All
foreign keys cascade on delete: removing a facility
removes its units and records, and removing a dataset removes its issues and the records it
last wrote.

\paragraph{Normalisation.} The schema is in third normal form apart from two deliberate
redundancies. First, \code{annual\_records.facility\_id} duplicates information derivable through
\code{units}, so that per-facility aggregates read a single indexed table rather than joining
through \code{units} for each of the 1,619 facilities. Second, the \SOtwo, \NOx, PM, and mercury
controls and the program code are stored on each annual record as reported for that year, as
the specification requires, while the unit also keeps the most recent values for display and
for records that arrive without them. The per-year values matter: in 16{,}233 of the 50{,}947 unit-years, the year's controls or programs differ from
the unit's current ones.

\subsection{Data flow and provenance}

Figure~\ref{fig:dataflow} shows how data enter and leave the database. The three entry
points, the Retrieve dialog, the Upload dialog, and the \code{sync:campd} script, converge on
one write path in \code{src/server/ingest.ts}. Before writing, it loads the stored metrics and
per-year attributes of every incoming facility-unit-year and classifies each record as new,
changed, or unchanged. It then upserts facilities, units, and annual records, computes the two
derived rates, replaces each record's sanity flags, and records the counts on the dataset row.
A record from a file without control columns keeps the controls already stored for that year,
or, if the year is new, takes the unit's current ones. Each import,
whether one uploaded file or one retrieved year, runs in a single database transaction, so a
failure part-way through leaves nothing behind. Source rows that fail
validation or repeat a facility-unit-year are written to \code{import\_issues} with their
original values and a reason.

Provenance is recorded at three levels. Each \emph{dataset} stores its source, time,
parameters (for API retrievals, the exact query as JSON), file name and archived copy (for
uploads), and the counts of rows received, stored, flagged, new, updated, unchanged, and
dropped. Each \emph{annual record} references the dataset that last wrote it, which the
interface shows as the record's origin; this is a coarse form of what Buneman et al.\ term
\emph{where-provenance}~\cite{buneman2001provenance}, identifying the source from which each
record was copied. Each \emph{issue} preserves a rejected or duplicate source row verbatim. A
dataset whose records have all been taken over by a later retrieval is retained and labelled
\emph{superseded}, so the retrieval history is never rewritten
(Section~\ref{sec:challenges}).

\section{Technical details}
\label{sec:technical}

\subsection{Languages}

Three languages are used. \textbf{TypeScript} implements the user interface, the server, the
query builders, and the command-line scripts; a single typed language across browser and
server lets tRPC carry the server's types into the React components
(Section~\ref{sec:discussion}). \textbf{SQL} is mostly generated by Drizzle, but the window
functions, correlated subqueries, and provenance conditions are written as SQL fragments
embedded in TypeScript. \textbf{Python} reads uploaded files, as the specification requires,
using the standard \code{csv} module and \code{openpyxl} for Excel workbooks.

\subsection{Database system}

The database is \textbf{SQLite}~\cite{gaffney2022sqlite}, accessed through the libSQL client
(\code{@libsql/client}). SQLite stores the whole database in one file, \code{db.sqlite}, which
is committed to the repository so that the application runs immediately after installation. It
provides every feature the design requires: foreign keys with cascading deletes, unique and
composite indexes, upserts (\code{INSERT \ldots{} ON CONFLICT DO UPDATE}), and window functions
such as \code{ROW\_NUMBER() OVER (PARTITION BY \ldots)}, which rank rows within groups in a
single pass over sorted input~\cite{leis2015window} rather than through self-joins or
application code. The libSQL client could also connect to a hosted libSQL server by changing
\code{DATABASE\_URL}, although the delivered system uses only the local file.

\subsection{Comparing the database with the EPA API before saving}
\label{sec:feat-retrieve}

Conventional data loaders write whatever the source returns. epaData instead treats retrieval
as a merge: it shows what a retrieval \emph{would} change and saves only once the user agrees,
answering the question a user has before retrieving, namely whether anything is new.

\paragraph{Example workflow.} The committed sample upload (Section~\ref{sec:feat-upload})
lowers one stored value, the 2023 \COtwo{} mass of Trimble County unit~2, from 4{,}099{,}943.863
to 4{,}098{,}943.863 short tons. After that upload, the user opens Retrieve and selects
Kentucky, facility~6071, and 2023:
\begin{enumerate}
  \item \emph{Already in the database} reports eight stored unit-years for 2023: two last
        written by the CSV upload and six by an earlier API retrieval.
  \item \emph{Preview} fetches the year from the API and compares each row with the stored
        record (Figure~\ref{fig:retrieve}): eight rows received, none new, one changed, seven
        unchanged, none dropped. The Changed tab names the field and both values,
        ``\COtwo: 4{,}098{,}943.86 $\to$ 4{,}099{,}943.86''.
  \item \emph{Approve \& save} stores the year as a new dataset; the history records 0~new,
        1~updated, 7~unchanged, and 0~dropped, and the EPA value is restored.
\end{enumerate}

\begin{figure}[H]
  \centering
  \includegraphics[width=0.92\linewidth]{retrieve-preview.jpg}
  \caption{Retrieval preview for Trimble County, 2023: the database panel (top), the API
  comparison with one changed record and its old and new value, and the approval button.}
  \label{fig:retrieve}
\end{figure}

\paragraph{Implementation.} Preview and save share one fetch function,
\code{fetchCampdAnnual}, which pages through the API, validates every row with Zod, removes
rows that repeat a facility-unit-year (including across pages), and writes nothing. The
comparison keys each record by its natural key (facility ID, unit ID, year) and compares the
seven metrics and five per-year attributes (Listing~\ref{lst:diff}). Values that differ only by
floating-point noise count as equal, so re-reading an unchanged CAMPD figure never registers as
a change, while a missing value differs from a reported zero. Rows
that fail validation or repeat a key are \emph{dropped} but not lost: saving writes them to
\code{import\_issues} with the Zod message as the reason, so the invalid-record report covers
API datasets as well as uploads. The save step re-fetches the year rather than trusting the
preview, fetches it completely before the first write, and then writes it in one transaction,
so neither a network nor a database failure leaves a partial dataset; a failed attempt is kept
in the retrieval history with its error.

\begin{lstlisting}[language=TypeScript, caption={Record comparison (\code{src/lib/record-diff.ts}), shared by retrievals and uploads.}, label=lst:diff]
/** Natural key of a unit-year record, shared by uploads, CAMPD rows, and stored records. */
export const recordKey = (facilityId: number, unitId: string, year: number | string) =>
  `${facilityId}:${unitId}:${year}`;

/** Equal within floating-point noise (relative 1e-9); null (not reported) equals only null. */
const sameMetric = (a: number | null, b: number | null) =>
  a === null || b === null
    ? a === b
    : Math.abs(a - b) <= 1e-9 * Math.max(1, Math.abs(a), Math.abs(b));

/** New when nothing is stored; otherwise every differing metric, and every per-year attribute the
 *  incoming record carries (uploads without control columns don't compare them). */
export function diffRecord(incoming: ComparableRecord, stored?: ComparableRecord) {
  if (!stored) return { status: "new", changes: [] };
  const changes = [
    ...TOTAL_KEYS.filter((k) => !sameMetric(incoming[k], stored[k])),
    ...RECORD_ATTRIBUTE_KEYS.filter(
      (k) => incoming[k] !== undefined && (incoming[k] ?? null) !== (stored[k] ?? null),
    ),
  ].map((field) => ({ field, database: stored[field] ?? null, incoming: incoming[field] ?? null }));
  return { status: changes.length ? "changed" : "unchanged", changes };
}
\end{lstlisting}

\subsection{Upload validation and the data-quality report}
\label{sec:feat-upload}

The upload path implements all eleven steps of the specification. Its distinguishing property
is that no row is lost: every row is stored, stored and flagged, or listed in the data-quality
report with a reason.

\paragraph{Validation rules.} \code{scripts/parse\_import.py} normalises each header by
lower-casing it and removing punctuation, so ``Facility ID'', \code{facility\_id}, and
\code{facilityId} all match the same alias list. It then maps the file to one of two schemas:
annual emissions (facility ID, unit ID, year, and metrics) or facilities and units (no year).
Each cell is converted by a column-specific rule (Listing~\ref{lst:parse}): identifiers and
years must be whole numbers within bounds, coordinates must lie within $\pm90$/$\pm180$
degrees, metrics must be non-negative, and states must be valid U.S.\ state or territory codes.
A row with any failing cell is rejected with every reason listed; a row whose
facility-unit-year already appeared earlier in the file is skipped as a duplicate with a
reference to the first occurrence.

\begin{lstlisting}[language=Python, caption={Cell validation in \code{scripts/parse\_import.py} (abridged).}, label=lst:parse]
def parse_value(col, raw):
    """Convert a non-empty cell to its database value, or raise ValueError with the reason."""
    if col == "stateCode":
        if raw.upper() not in US_STATES:
            raise ValueError(f"Unrecognized US state or territory '{raw}'")
        return raw.upper()
    if col not in BOUNDS:
        return raw
    lo, hi, whole = BOUNDS[col]          # e.g. year: (1980, 2100, True)
    try:
        n = float(raw.replace(",", ""))
    except ValueError:
        n = math.nan
    if not math.isfinite(n):
        raise ValueError(f"Expected a number, got '{raw}'")
    if whole and not n.is_integer():
        raise ValueError(f"Expected a whole number, got '{raw}'")
    if n < lo or (hi is not None and n > hi):
        raise ValueError(f"Out of range ({lo} to {hi})" if hi is not None else f"Must be at least {lo}")
    return int(n) if whole else n
\end{lstlisting}

\subsection{Description-based search}
\label{sec:feat-describe}

The rubric asks for a search that understands requests such as ``Find coal units in Kentucky
with high CO2 emissions.'' A large language model could translate such a sentence, but it would
make the core search depend on a network service and an API key, and its output may vary
between runs. epaData therefore uses a deterministic, rule-based parser
(\code{src/lib/describe-search.ts}) and consults a language model only for words the parser
could not use, and only if a key is configured.

\paragraph{Algorithm.} The parser performs entity extraction rather than template matching, so
word order does not matter. It operates in two passes (Listing~\ref{lst:describe}).

\begin{lstlisting}[language={}, caption={Outline of the description parser.}, label=lst:describe, numbers=none]
vocabulary <- filter values from the database (states, fuels, unit types, controls,
              counties, statuses) + synonyms ("scrubber" -> FGD, "gas" -> Natural Gas,
              state names -> codes) + metric, comparator, ranking, and view words

pass 1: tokens -> items
  for each position, take the LONGEST phrase (up to 6 words) found in the vocabulary
    ("west virginia" beats "virginia"; "natural gas" beats "gas")
  two-letter state codes count only in capitals ("IN", not "in")
  counties need the word "county"; names follow "owned by" / "named"
  numbers: 500,000 | 500k | 1.2M | 5e5; four-digit years
  unknown filter value within edit distance 1 (2 for long words) -> fuzzy match
  "not X" -> reported as not understood, never inverted
  anything else that is not a stopword -> not understood

pass 2: bind items
  filters -> filter values;  "units" / "plants" -> which table to show
  comparator + number -> nearest metric word, looking forward then back
     ("over 500k tons of CO2", "CO2 over 500k", "under 50 tons SO2")
  year-like numbers -> year, or year range ("since 2020", "2015-2020")
  "top / highest / most [N]" -> sort descending, keep N (default 10, or 1 if singular)
  "lowest / least / cleanest [N]" -> sort ascending;  "in each state" -> rank per state
  "high / low <metric>" without a number -> qualitative term, resolved on the server
\end{lstlisting}

Typo tolerance uses the optimal-string-alignment variant of edit distance, which counts
insertions, deletions, substitutions, and adjacent transpositions, the four error types
Damerau identified as the bulk of spelling mistakes~\cite{damerau1964}. It applies only to
filter values of five or more letters, so short words are never ``corrected'' into something
else.

\paragraph{Resolving ``high'' and ``low''.} A qualitative term has no fixed numeric meaning:
500{,}000 tons of \COtwo{} is high for a gas turbine and low for a large coal unit. The server
therefore resolves ``high $m$'' and ``low $m$'' to the 75th and 25th percentiles of metric $m$
over the unit-years matching all \emph{other} filters. With the $n$ matching values in ascending
order, $x_{(0)} \le \dots \le x_{(n-1)}$, the thresholds are the order statistics
\begin{equation}
  t_{\text{high}} = x_{(\lfloor 0.75\,(n-1) \rfloor)}, \qquad
  t_{\text{low}} = x_{(\lfloor 0.25\,(n-1) \rfloor)},
\end{equation}
each obtained with a single \code{ORDER BY $m$ LIMIT 1 OFFSET $k$} query. This is the simplest
of the sample-quantile definitions compared by Hyndman and Fan~\cite{hyndman1996quantiles}:
where their common default interpolates between neighbouring order statistics, epaData takes
the lower one, so the threshold is computed from a value present in the data rather than an
interpolated one. Unit-years that do not report the metric are excluded, as they have no value
to rank. The threshold is then rounded to three significant figures for readability, becomes an
ordinary minimum or maximum filter, and sorts the table by that metric. For the rubric
sentence, the 385 of 416 Kentucky coal unit-years that report \COtwo{} give
$t_{\text{high}} = 2{,}720{,}000$ tons, which selects 97 unit-years (Figure~\ref{fig:describe});
the interface states the rule beside the result (``high = top 25\% of unit-years matching the
other filters'').

\begin{figure}[H]
  \centering
  \includegraphics[width=0.92\linewidth]{describe.jpg}
  \caption{Description search on the committed database. The sentence becomes three removable
  filter chips; the note explains the threshold; 97 unit-years match, sorted by \COtwo.}
  \label{fig:describe}
\end{figure}

\paragraph{Language-model fallback.} When words remain unrecognised and
\code{OPENROUTER\_API\_KEY} is set, \code{src/server/llm-search.ts} sends the sentence, the
parser's interpretation, and the leftover words to an OpenRouter model, requesting structured
JSON whose schema enumerates the database's own filter values. The model may only \emph{add}
filters the parser did not set; every returned value is re-validated with Zod against the
vocabulary; the call times out after 8 seconds; and any failure falls back to the parser's
result with a note. The model therefore cannot introduce a value absent from the database, and
the search remains fully functional without it.

\subsection{Multi-constraint search and ranking in SQL}
\label{sec:feat-ranking}

The specification's example, ``coal-fired units in Kentucky in 2025 with annual \COtwo{}
emissions greater than 500{,}000 short tons'', is a conjunction of conditions on the facility
(state), the unit (fuel), and the unit-year (year and \COtwo). The query builder has one
function per level and combines their output with AND (Figure~\ref{fig:multi}). Fuel,
unit-type, and control filters match by substring, because CAMPD stores combined values such as
``Coal, Pipeline Natural Gas'' or ``Wet Lime FGD|Wet Limestone''; operating status matches by
prefix, so that ``Retired'' does not also match ``Operating (Retired 04/15/2016)''.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.92\linewidth]{units-multi.jpg}
  \caption{Multi-constraint search: KY, Coal, 2025, \COtwo{} $\ge$ 500{,}000\,t. The chips, the
  open \emph{More filters} panel with its range inputs, and the first rows of the 25 results.}
  \label{fig:multi}
\end{figure}

Ranking is implemented with a window function. Listing~\ref{lst:rank} shows, simplified, the
SQL that \code{rankedUnitYears} generates for ``the highest-\COtwo{} coal unit-year in each
state in 2025''. The inner query numbers the matching rows in sort order, restarting for each
state when ranking per state, and the outer query keeps the first $N$ ranks. The page of rows,
the total count, and the CSV export all derive from this one subquery and therefore always
agree. \code{IS NULL} in the ordering places missing values last in either direction, and the
record ID breaks ties so that paging is stable.

\begin{lstlisting}[style=sql, caption={Ranking query generated for a per-state top-1 search (simplified).}, label=lst:rank]
SELECT * FROM (
  SELECT ar.id, f.name, f.state_code, u.unit_id, ar.year, ar.co2_mass_tons, d.source AS origin,
         ROW_NUMBER() OVER (
           PARTITION BY f.state_code                      -- only when ranking per state
           ORDER BY ar.co2_mass_tons IS NULL, ar.co2_mass_tons DESC, ar.id
         ) AS rank
  FROM annual_records ar
  JOIN units u       ON ar.unit_internal_id = u.id
  JOIN facilities f  ON ar.facility_id = f.id
  LEFT JOIN datasets d ON ar.dataset_id = d.id
  WHERE lower(u.primary_fuel) LIKE '%coal%'           -- unit condition (contains)
    AND ar.year = 2025                                -- record conditions
) AS ranked
WHERE rank <= 1                                       -- keep the first N
ORDER BY state_code, rank
LIMIT 25 OFFSET 0;                                    -- one page
\end{lstlisting}

The Facilities view ranks plants by totals computed with correlated subqueries, for example
the sum of \COtwo{} over a facility's records in the selected year. Unit and unit-year filters
retain a facility if at least one of its unit-years matches, expressed as an \code{IN} subquery
so that the facility row is not duplicated. Figure~\ref{fig:ranking} shows the per-state
ranking for 2024.

\subsection{Physical-sanity audits}
\label{sec:feat-audits}

Validation detects malformed values but not values that are well-formed yet physically
implausible. epaData therefore applies four rules to every annual record it writes, whatever
its source. Let $H$ be heat input (MMBtu), $G$ gross load (MWh), $T$ operating time (hours),
and $C$ the \COtwo{} mass (short tons). The derived rates stored with each record are
\begin{equation}
  \text{heat rate} = \frac{H}{G}\ \ \text{MMBtu/MWh}, \qquad
  \text{\COtwo{} intensity} = \frac{2000\,C}{G}\ \ \text{lb/MWh},
\end{equation}
both undefined (stored as \code{NULL}) when $G = 0$ or an input is not reported. Writing
$\varnothing$ for a value that was not reported, the rules, with thresholds defined once in
\code{AUDIT\_THRESHOLDS}, are:
\begin{align}
  \texttt{ZERO\_EMISSIONS\_HIGH\_HEAT} \;(\text{ERROR}):&\quad H > 1000 \ \wedge\ C = 0,\\
  \texttt{CO2\_NOT\_REPORTED} \;(\text{WARN}):&\quad H > 1000 \ \wedge\ C = \varnothing,\\
  \texttt{PHANTOM\_GENERATION} \;(\text{ERROR}):&\quad G > 0 \ \wedge\ T = 0,\\
  \texttt{EXTREME\_HEAT\_RATE} \;(\text{WARN}):&\quad H/G < 5 \ \vee\ H/G > 25.
\end{align}
A comparison involving $\varnothing$ is false, so a rule never fires on a missing input. The
first rule reflects that burning fossil fuel always produces \COtwo, so a reported zero is
implausible, whereas the second records a reporting gap; the third reflects that a unit cannot
generate without operating; the fourth bounds the heat rate by the range of real
fossil plants, from about 6.5\,MMBtu/MWh for modern combined-cycle units to 15--18\,MMBtu/MWh
for old peaking units. Flagged records are retained and appear in the Audits tab, the unit and
facility dialogs, and the invalid-record export. In the committed database the rules raise
6{,}909 flags on 6{,}432 records: 6{,}105 records with heat input but no reported \COtwo{} and
804 extreme heat rates, all warnings. Most of the former are gas- and oil-fired units, and
2{,}637 of them also report no gross load. No record reports a \COtwo{} mass of exactly zero
alongside significant heat input, so no ERROR is raised (Section~\ref{sec:challenges}).

\subsection{Approach}

The system was tested at four levels:
\begin{enumerate}
  \item \textbf{Static checks.} \code{npm run validate} runs Prettier, ESLint, the TypeScript

        after every development stage. Because database rows, procedure inputs, and component
        props share types, type checking catches a large class of errors early.

        HTTP, and the interface was driven by a scripted headless browser, which also produced
        the screenshots in this report. These runs used copies of \code{db.sqlite}, leaving the

\subsection{Known issues}

A final audit of this report against the code found several defects, all of which were
corrected. Uploading a CAMPD daily file, which has no year column, keyed each row by facility and
unit alone, so every day after the first was reported as a duplicate: a 359{,}723-row file
produced 355{,}770 spurious issue rows. Sub-annual rows are now identified by their date and
hour, and a regression test covers the case. Imports were not transactional, so a database
error part-way through could leave a partial dataset; each import now commits or rolls back as a
whole, which a deliberately failing import confirmed. Missing metrics were stored as zero, which
turned 6{,}105 unreported \COtwo{} values into zero-emission errors; they are now stored as
\code{NULL} and flagged as warnings (Section~\ref{sec:challenges}). In the interface, the
comparison dialog labelled gross load as ``Net Generation''; the upload report counted rows
already in the database as duplicates; the map omitted facilities without coordinates without
saying so; and the shared dialog component lacked dialog semantics. It now declares
\code{role="dialog"}, moves focus into the dialog, keeps Tab within it, closes only the topmost
of stacked dialogs on Escape, and restores focus on close. These behaviours were verified in a
headless browser.

One issue remains: the language-model fallback was tested only on its failure paths (no key,
invalid key, timeout), since no OpenRouter key was available during testing.

\section{Discussion}
\label{sec:discussion}

\subsection{Effectiveness of techniques and tools}

\paragraph{SQL for search and ranking.} The specification's top-$N$, bottom-$N$, and
group-and-rank searches are a natural fit for window functions. Computing ranks in the
database rather than in TypeScript means that pagination, the total count, and the CSV export
derive from one ranked subquery and cannot disagree, and that only one page of rows ever leaves
the database. The percentile thresholds of the description search benefit similarly: a single
\code{ORDER BY \ldots{} LIMIT 1 OFFSET $k$} query is simpler and faster than loading the values.

\paragraph{Python for reading files.} The requirement to read uploads with Python proved
sensible: the \code{csv} module and \code{openpyxl} handle encodings, byte-order marks, quoted
fields, Excel dates, and typed cells with little code. Running the parser as a subprocess with a
JSON interface kept the boundary simple: Python decides what a valid row is, and TypeScript
decides what to do with it.

\paragraph{One write path in TypeScript.} The most valuable structural decision was to give
retrieval, upload, and the command-line sync a single write path. Because diffing, upserting,
deriving rates, auditing, and issue logging are implemented once in \code{ingest.ts}, the
database-versus-API comparison worked for uploads as soon as it was added, and any fix to the
audit rules applies to every source. Static types made such refactoring safe, since changing a
record type surfaced every affected call site at compile time.

\paragraph{Validation at every boundary.} Every value entering the server from outside,
whether a procedure input, a CAMPD row, an environment variable, or language-model output, is
parsed with a Zod schema before use, so malformed input fails at the boundary with a readable
message rather than deep inside a query.

\subsection{Technical choices and alternatives}

\paragraph{Next.js, tRPC, and Drizzle instead of Flask, Jinja, and SQLAlchemy.} The course
suggests Flask with Jinja templates and SQLAlchemy; the team's proposal specified a Next.js
stack instead. The motivation was interactivity: the explorer updates results as filters
change, keeps its state in the URL, and opens nested dialogs, all of which would require a
separate JavaScript layer on top of server-rendered Jinja pages. With one language and tRPC,
the server's procedure signatures are the client's API, so a renamed filter or changed result
field becomes a compile error rather than a runtime bug. The cost is a second language for file
parsing and a subprocess boundary. Each element of the suggested stack has a direct
counterpart (route handlers and procedures for Flask routes, React components for templates,
Drizzle for SQLAlchemy, and the same SQLite database), so the objectives concerning routes,
templates, forms, and an object-relational mapper are met with equivalent tools.

\paragraph{Drizzle instead of Prisma.} Prisma's query API describes results as nested objects
and can express a window function or correlated subquery only through raw SQL strings, which
forgo type checking. Drizzle composes queries from typed SQL fragments, so the ranking
expression, the per-facility subqueries, and the provenance conditions are ordinary,
type-checked code; it also generates readable SQL migrations from the TypeScript schema.

\paragraph{A rule-based parser instead of a language model.} A language model would handle more
varied phrasing with less code. The rule-based parser was nevertheless chosen as the primary
method because it is deterministic, requires no network or key, answers in milliseconds, can be
unit-tested exactly, and can only produce values that exist in the database. Its limitation is
coverage, since unanticipated phrasing is reported rather than understood. The optional fallback
combines the strengths of both: the model sees only the leftover words and may only add
vocabulary values, extending coverage without making the core behaviour unpredictable.

\paragraph{Preview-then-save instead of direct synchronisation.} The first version of retrieval
wrote immediately. The preview costs a second request to the EPA API on save, about two seconds
for a full year, but in return the user sees exactly what will change before anything is
written, and an interrupted fetch can no longer leave a partial dataset. Where provenance
matters, this is the better default; the command-line sync still writes directly for scripted
refreshes.

\paragraph{One page with dialogs instead of separate pages.} Realising the specification's six
pages as views and dialogs within one page keeps the user's search in place while they
retrieve, upload, inspect, or download, and every search remains reproducible through its URL.
The trade-off is that the dialogs themselves are not addressable by URL.

\paragraph{Storing annual data, fetching sub-annual data.} Storing hourly data for every unit
would require tens of millions of rows per year. Since Phase~1 searches operate on annual
records, only those are stored; the granular views fetch hourly to monthly data on demand and
cache it in the browser.

\subsection{Challenges and lessons learned}
\label{sec:challenges}

\paragraph{Combined attribute values.} CAMPD's master-data endpoints list single values such
as ``Coal'' or ``Wet Limestone'', but unit records often contain combinations such as ``Coal,
Pipeline Natural Gas'' or ``Wet Lime FGD|Wet Limestone'', so equality filters missed many
units. Combined values are therefore split into distinct dropdown options, and fuel, type, and
control filters match by case-insensitive substring. For the same reason, the ``Already in the
database'' panel can only approximate what an API request with a fuel or control filter will
return, which the dialog states.

\paragraph{Superseded datasets.} Because records are keyed by facility, unit, and year,
re-retrieving a year moves its records to the new dataset and leaves the old one owning
nothing. Deleting the old dataset would erase history, while counting it as active would double
the coverage figures. The adopted rule labels an API dataset \emph{superseded} when it once
stored records but now owns none; only active datasets are counted, and superseded ones remain
visible in the retrieval history.

\paragraph{Generated SQL.} The first implementation of that rule returned wrong results.
Drizzle omits table prefixes in single-table queries, so in \code{SELECT \ldots{} FROM datasets
WHERE NOT EXISTS (SELECT 1 FROM annual\_records WHERE dataset\_id = id)} the unqualified
\code{id} bound to \code{annual\_records.id} rather than \code{datasets.id}. Qualifying these
subqueries by hand fixed the defect. The lesson is to inspect the SQL an ORM generates whenever
a query relates two tables in a non-trivial way.

\paragraph{Ambiguity in natural language.} Several two-letter state codes are also common
English words (``in'', ``or'', ``me'', ``ok''); treating them as states would turn ``units in
Texas'' into a search for both Indiana and Texas. The parser therefore accepts these codes only
in capitals, while full state names and unambiguous codes work in any case. A similar ambiguity
exists in the data: the status ``Operating (Retired 04/15/2016)'' contains the word
``Retired'', so the status filter uses a prefix rather than a substring match.

\paragraph{Extent of EPA's data.} CAMPD publishes the current year quarterly, and requests
beyond the last published quarter fail. No endpoint reports this date, but the API's error
message names it (``\ldots{} the quarter ending on 06/30/2026''). The client therefore probes
with a full-year request, parses the date from the error, caches it for an hour, and uses it to
bound the date pickers of the granular view; if EPA publishes a new quarter while the
application runs, a failing request reveals the new date and is retried once.

\paragraph{Missing is not zero.} The first schema declared every metric \code{NOT NULL DEFAULT 0},
which kept sums simple but silently turned a value CAMPD had left blank into a measured zero.
The zero-emissions rule then reported 6{,}105 errors that were in fact reporting gaps, and the
heat-rate rule flagged 51 records whose ``extreme'' rate came from a missing heat input. Making
the columns nullable, storing blanks as \code{NULL}, and adding a separate warning for an
unreported \COtwo{} removed every one of these false errors after a re-sync of all twelve years.
The lesson is that absence must be modelled explicitly whenever later logic distinguishes ``none''
from ``unknown''.

\paragraph{Measuring performance.} The year-filtered ranking defect (Section~\ref{sec:perf})
went unnoticed because every query was fast without a year filter. Indexing each foreign key is
not sufficient: indexes should match the combinations of columns that queries filter on
together, and the planner's choice should be verified rather than assumed.

\paragraph{General lessons.} Three practices paid off repeatedly. Keeping logic free of
database and network access made it testable with fast unit tests. Maintaining one code path
per concern (one write path, one CSV writer, one ranked query per view) meant that fixes applied
everywhere at once. Finally, never discarding data, by retaining rejected rows, flagged records,
and superseded datasets, made every count in the interface explainable.

\section{Limitations and future improvements}
\label{sec:limitations}

\subsection{Current limitations}

\paragraph{Fuel and unit type are not versioned by year.} Controls and program codes are stored
per unit-year, but fuel and unit type are stored once per unit, and the latest import's values
prevail. They change rarely, but when they do, history is lost. Big Sandy unit BSU1, for
example, reported coal as its primary fuel in 2014 but natural gas today, so epaData shows it as
a gas unit in every year and a search for coal units in 2014 would miss it.

\paragraph{Records are overwritten, not versioned.} Each facility-unit-year has one stored
value, and re-importing it overwrites the metrics and reassigns the record to the new dataset.
The dataset's counts record \emph{that} a change occurred and the preview shows \emph{what}
changed, but after saving the previous value is lost.

\paragraph{Origin is known per unit-year only.} Facility and unit rows have no link to the
dataset that created or last modified them, so the Origin filter applies only to annual
records.

\paragraph{Local, single-user deployment.} The application runs on one machine against one
SQLite file and has no user accounts, so anyone who can open it can upload files and run
retrievals. An early attempt at serverless hosting required copying the database to temporary
storage on every cold start, which loses writes, and was abandoned.

\paragraph{Description search has fixed coverage.} The parser does not express negation (``not
retired''), alternatives (``coal or gas''), or comparisons between entities (``units larger than
Gavin''); such phrases are reported as not understood. Facility names are recognised only after
cue words such as ``owned by'' or ``named''.

\paragraph{Upload formats.} Uploads recognise the CAMPD annual-emissions and facility-attribute
layouts. Hourly and daily files are read, with each row identified by its unit and period, but
only their facility and unit attributes are stored, because the schema has no place for
sub-annual metrics.

Finally, map clustering and year-over-year spike detection from the proposal were not built
(Table~\ref{tab:changes}).

\subsection{Future improvements}

\paragraph{Phase 2: evaluation.} The next phase adds the remaining tables of the
specification: TRACI characterisation factors, indicator definitions, calculated indicators,
weight scenarios with their weights, and score results. The existing design supports this
directly. Indicators are functions of the stored annual records (for example, \SOtwo{} mass
multiplied by its acidification factor), so they can be computed with the same ranked queries,
exported through the same CSV path, and linked to the dataset of the records from which they
were computed.

\paragraph{Data model.} Fuel and unit type can be moved onto the annual record in the same way as
the controls, since the annual API rows already contain them. A history table receiving every
overwritten annual record, together with the dataset that replaced it, would make changes
auditable after saving.

\paragraph{Data quality.} Year-over-year anomaly detection, flagging a unit whose emissions
change by more than a set number of standard deviations of its own history, would complement
the physical rules, and a review state on audit flags (open, accepted, or explained) would let
analysts record their conclusions.

\paragraph{Search.} Negation and alternatives can be added to the filter model as exclusion and
multi-value filters, onto which the parser can then map ``not'' and ``or''. Named saved searches
would complement the shareable URLs.

\paragraph{Deployment and access.} Hosting the database on a libSQL server, which the client
library already supports, would permit a shared deployment. This would also require user
accounts with upload and retrieval restricted to authorised users, and background jobs for
multi-year retrievals.
